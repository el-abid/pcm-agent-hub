Ce document décrit le fonctionnement du hub, pas les URLs de staging. Les schémas restent valables même quand la plateforme est indisponible.

1 · L'idée en une phrase

A2A est la langue que les agents utilisent pour se parler. L'orchestrateur ne fait pas le travail lui-même : il envoie la question aux agents spécialisés, attend leurs réponses, puis assemble le tout.

Analogie : imaginez un standard téléphonique. L'opérateur (l'orchestrateur) reçoit l'appel, appelle le bon service (documentation, équipements, annuaire), puis répond au client avec la synthèse. A2A est le langage commun que tous les services utilisent pour se comprendre.

Les quatre mots à connaître

L'orchestrateur parle aux quatre agents avec le même protocole A2A.

2 · La carte de visite : AgentCard

Avant de parler à un agent, il faut savoir qui il est et ce qu'il sait faire. C'est le rôle de l'AgentCard. C'est un petit fichier JSON, public, que la gateway sert à une adresse fixe.

La carte de visite dit où joindre l'agent et ce qu'il sait faire.

Chaque agent du projet a une carte : docs-agent, equipment-agent, degraded-agent, support-agent, critic-agent, etc. Les cartes sont aussi exportées dans agent-cards/.

À retenir : l'AgentCard ne fait pas le travail. Elle sert seulement à découvrir l'agent et à savoir comment lui parler.

3 · Un appel A2A en 6 étapes

Un appel A2A est un échange de messages. L'orchestrateur envoie une question, la gateway transmet à l'agent, puis la réponse remonte sous forme de Task.

Le même schéma vaut pour les quatre agents : seule l'adresse change.

Ce qui circule réellement

  • La question : un texte simple, par exemple « Porte bloquée, que faire ? ».
  • L'adresse : POST /docs-agent, /equipment-agent, etc.
  • La réponse : un Task avec un état completed et un texte final.

4 · Les nodes dans Langflow

Dans le flow PCM Agent · Fanout, l'orchestrateur n'est pas un seul gros agent. C'est un enchaînement de briques visuelles, les nodes. Chaque brique fait une seule chose.

Le fan-out : quatre appels parallèles, puis un seul chemin de critique et de révision.

Les champs d'un node A2A Call

ChampRôleExemple
Hub URLAdresse de la gatewayhttps://gateway.trycloudflare.com

Bearer TokenMot de passe partagéla variable a2a_bearer_token
MessageTexte envoyéla question de l'utilisateur
Ce que fait le node : il envoie un POST JSON-RPC à Hub URL + / + Agent, avec le texte dans message.parts. La gateway répond avec un Task. Le node transforme le texte du Task en Message, que le node suivant peut lire.

5 · Deux façons d'orchestrer

Le projet a connu deux versions. Le protocole A2A est le même, seule la façon de décider change.

Version agentique

Un agent LLM reçoit la question et choisit quel outil appeler. Chaque outil est un agent A2A.

  • Plus souple : il peut n'appeler qu'un agent.
  • Dépend du tool calling du modèle.
  • Moins prévisible avec les modèles gratuits.

Version fan-out actuelle

Le flow appelle toujours les quatre agents, en parallèle. Puis il combine, critique et révise.

  • Plus prévisible et plus rapide.
  • Ne dépend pas du tool calling.
  • Appelle les quatre agents même si un seul suffit.

Même protocole A2A. Seule la décision d'appeler change.

6 · Le message A2A, en clair

Un message A2A est du JSON. Il tient en trois idées : qui parle, à qui, et quel texte. 

{
  "jsonrpc": "2.0",
  "id": "demo-1",
  "method": "message/send",
  "params": {
    "message": {
      "kind": "message",
      "role": "user",
      "parts": [
        { "kind": "text", "text": "La porte du quai 2 est bloquée." }
      ]
    }
  }
}

La gateway répond avec un Task :

{
  "jsonrpc": "2.0",
  "id": "demo-1",
  "result": {
    "kind": "task",
    "status": { "state": "completed" },
    "artifacts": [
      {
        "parts": [
          { "kind": "text", "text": "Sécurisez la zone, informez le PCC..." }
        ]
      }
    ]
  }
}

Trois détails qui comptent

  • id : permet de faire le lien entre la question et la réponse.
  • parts : le texte est découpé en morceaux, pour pouvoir ajouter des fichiers plus tard.
  • status.state : dit si la tâche est en cours, terminée ou en erreur.
Ne pas confondre : A2A sert à parler entre agents. MCP sert à donner des outils à un agent (par exemple écrire dans MongoDB Atlas). Les deux sont complémentaires.

7 · Le trajet complet d'une question

  1. L'opérateur écrit sa question dans le Playground ou via l'API.
  2. Le flow PCM Agent · Fanout reçoit la question dans Chat Input.
  3. Quatre nodes A2A Call envoient la question à la gateway, chacun vers un agent.
  4. La gateway vérifie le jeton, retrouve le flow de l'agent et le lance.
  5. Chaque agent cherche dans pcm_doc avec Astra DB et répond avec ses sources.
  6. La gateway renvoie un Task à chaque node. Les quatre réponses reviennent.
  7. Combine Text assemble la question et les quatre réponses.
  8. Critique vérifie la sécurité, l'ancrage et les placeholders.
  9. Révision corrige, Contact Enricher restaure les numéros exacts.
  10. La réponse finale est publiée. La passerelle journalise la question et la réponse dans Atlas via MCP.
Point clé : l'orchestrateur ne « connaît » pas les agents. Il connaît seulement leur adresse A2A et la gateway. C'est ce qui rend le hub interopérable : on peut remplacer un agent par un autre service qui parle A2A, sans changer le reste du flow.

Une question, quatre regards spécialisés, une réponse contrôlée.

8 · Les agents et leurs rôles

AgentCe qu'on lui demandeCe qu'il répond
DocumentationLa procédure, les étapes, la sécurité.E1 à E4, sources PROC-PAL-001.
ÉquipementsQuel organe vérifier et comment.EQ-PSD-ALIM, CTRL, OBS, points de contrôle.
Modes dégradésQuelle solution de secours appliquer.D1, D2, D3, décision PCC.
AnnuaireQui appeler et quand.Numéros exacts, horaires, conditions.
CritiqueLa réponse est-elle sûre et sourcée ?Verdict JSON : APPROVED ou REVISE.

Le critique ne répond pas à l'utilisateur. Il relit la réponse des autres. C'est la partie « auto-réflexion » : on vérifie avant d'envoyer.

Ce que l'agent ne fait pas

  • Il ne commande pas de pièce.
  • Il n'invente pas de numéro de téléphone.
  • Il ne remplace pas une habilitation ou une consigne de sécurité.
  • Il escalade si la situation dépasse le périmètre.

9 · Pourquoi c'est interopérable

Un contrat stable

Tous les agents parlent le même langage : AgentCard, JSON-RPC, message/send, Task. On peut remplacer un agent par un autre service qui respecte ce contrat.

Une gateway unique

Les agents n'exposent pas leur complexité. La gateway cache Langflow, les flows, les modèles et les credentials derrière une adresse stable.

MCP à côté

MCP sert aux outils : lire ou écrire dans MongoDB Atlas. A2A sert à parler entre agents. Les deux sont séparés, donc on peut changer l'un sans casser l'autre.

Traçabilité

Chaque appel laisse une trace : agent, durée, contexte, statut. Chaque réponse de l'orchestrateur est journalisée dans Atlas.

Les limites à connaître

  • La gateway et les tunnels doivent rester actifs.
  • Les URLs de tunnel changent après un redémarrage.
  • Le quota gratuit OpenRouter limite le nombre de tests.
  • Les flows publics de démonstration doivent être refermés après la démo.
Sécurité : le jeton Bearer protège les routes A2A. Ne le mettez pas dans un prompt. Le serveur MCP en écriture doit être coupé après la démonstration.

10 · Récapitulatif

Agent
Un service qui a un métier, un prompt et des outils.
AgentCard
La carte de visite JSON de l'agent : nom, adresse, compétences.
A2A
Le protocole JSON-RPC qui permet à deux agents de se parler.
Gateway
La passerelle qui reçoit les appels A2A et lance le bon flow Langflow.
Task
La fiche de réponse : état, texte final, identifiant.
Fan-out
Appeler plusieurs agents en parallèle, puis assembler leurs réponses.
Critique
L'agent qui relit la réponse et renvoie un verdict avant l'envoi.
La phrase à retenir : l'orchestrateur ne fait pas tout. Il parle A2A, la gateway traduit, les agents travaillent, le critique vérifie. C'est cette séparation qui rend le hub lisible, testable et remplaçable.
